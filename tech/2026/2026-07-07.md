### Security Certificate Model Example

Steven presented issues related to the Security Certificate Model example, including use of parameters for cryptographic algorithms.

Relevant issue: https://github.com/spdx/cryptographic-algorithm-list/issues/39

Parameters discussed included `parameterName` values such as:

- `padding`
- `paddingScheme`
- `digestFunction`
- `keyLength`

The group discussed whether SPDX should define constraints for cryptographic parameters or use a simpler form initially.

Kate noted that adding constraints now may be premature. She suggested using a simple, short form first and iterating if community demand develops.

Karsten noted that the purpose of the cryptographic list is to provide constraints. He questioned the value of a cryptographic list if only a simple form is used, and stated that the group needs to determine how parameters can be useful.

Greg noted that `parameter` should not be overloaded because other profiles may use it. Kate agreed. The group discussed using a more specific term, such as `cryptoParameters`.

Joshua recommended implementing the minimum needed now and avoiding additions unless there is clear evidence they are required.

Karsten referenced his mapping work as an example of why some algorithms are disallowed: https://github.com/org-metaeffekt/metaeffekt-cryptography/blob/main/cryptographic-algorithm-status.md

The group discussed whether the model should be more specific regarding mode of operation.

Steven noted that this is critical because of regulatory requirements. The specific applicable regulation needs to be clarified.

Bob clarified that there is no cryptographic profile. There is a cryptographic list that may be used by the Security, Operations, and Build profiles.

Art asked whether the cryptographic list should live outside the SPDX specification ecosystem, similar to the SPDX License List, with a stable URI or IRI for each entry and a separate URL namespace and versioning approach. Steven responded that IRIs already exist for each cryptographic algorithm.

The group discussed whether the grammar for the cryptographic list should initially follow the License List.

For license expressions, the relevant operators are:

- `AND`
- `OR`
- `WITH`

For cryptographic expressions, the group discussed:

- `AND`
- `OR`
- `SET`

Karsten recommended starting with only `AND` and `OR`, then considering additional operators over time.

For cryptographic algorithms not present in the SPDX Cryptographic List, the group discussed using a set of classes and properties to define a custom cryptographic algorithm, similar to custom licenses.

Steven noted that SPDX must differentiate between certificates and signatures, including how to represent “signed by” in SPDX.

### Proposed New Item: `hasInstall` and `hasUninstall`

PR: https://github.com/spdx/spdx-3-model/pull/1297

Joshua described the root file system image use case. A root file system image may contain files, and those files may come from a package. Currently, the available relationship is `contains`. It would be useful to record what installed the files.

The group also discussed the need to track uninstall information, including how something can be uninstalled or what performed the uninstall.

Steven asked whether the Action classes and properties from SupplyChain could be used, including information such as when an action started, when it finished, and who performed it.

Joshua noted that the host platform is already addressed by the Build profile.

The group discussed `LifecycleScopedRelationship`.

The group noted that the Build profile may need to be reviewed in relation to SupplyChain, potentially in SPDX 4.

The definition of “install” requires further clarification. Open questions included:

- Whether decompressing something into a directory counts as installation.
- Whether cross-compiling something counts as installation.
- How to distinguish installation with a package manager from installation without a package manager.
- Whether the installed artifact can indicate the installer, such as `npm`.
- Whether “installed by” is primarily a deployment and operational concept.
- Whether the safety view should also be considered.
- Whether installation mode should be represented, including at least `push` and `pull`.
